# Technical Protocol Specification for MQTT Data Access of iSolarInsight Portal

## 1. Document Overview

### 1.1 Document Purpose

This document specifies the MQTT protocol-related technical requirements for the access of non-Sungrow systems/equipment (EMS, PPC, etc.) to the iSolarInsight Portal (hereinafter referred to as the "Platform"), including access preparation, connection parameters, topic definition, message format, data encoding, security specifications, exception handling, and test acceptance. Access parties shall strictly comply with this specification for data access development to ensure the stability, security and consistency of data transmission.

### 1.2 Scope of Application

This specification applies to all systems, IoT devices and relevant developers that report data to the Platform via the MQTT protocol.

### 1.3 Terms and Definitions

| Term/Abbreviation |                          Definition                          |
| :---------------: | :----------------------------------------------------------: |
|       MQTT        | Message Queuing Telemetry Transport, a lightweight IoT communication protocol based on the publish/subscribe model |
|      Broker       | MQTT server, responsible for receiving messages published by clients and forwarding them to clients subscribed to relevant topics |
|      Client       | MQTT client, including the access party's devices/systems (publishers) and the Platform (subscribers), or the Platform (publishers) and the access party's devices/systems (subscribers) |
|       Topic       | MQTT message topic, used to identify message categories; clients receive corresponding messages by subscribing to topics |
|        QoS        | Quality of Service, used to define the reliability level of message transmission |

### 1.4 Reference Standards

[1] MQTT Version 3.1.1 (OASIS Standard, 2014)

## 2. Access Preparation

### 2.1 Access Qualification Application

The access party shall submit an access application to the Platform operator and provide the following information:

1. Name of the access subject (enterprise/institution/individual);
2. Type and quantity of access devices/systems;
3. Scope and purpose of data transmission;
4. Contact person and contact information.

After the Platform's approval, a unique **Client ID**, **Username**, **Password**, certificate and power station ID will be assigned for MQTT connection authentication.

### 2.2 Environmental Requirements

1. Network environment: The access party's devices/systems shall ensure network connectivity, support the TCP/IP protocol, and be able to access the Platform's MQTT server address;
2. Protocol version: Support MQTT 3.1.1;
3. Device resources: Ensure that the devices have sufficient storage, computing and network bandwidth resources according to the QoS level and data transmission frequency. Recommended bandwidth: 50 Mbps for power stations with a capacity of 600 MWh and below; 100 Mbps for power stations with a capacity of more than 600 MWh and up to 1,200 MWh.
4. Note: The above bandwidth recommendations apply only to the data traffic generated by the iSolarInsight Portal. The actual bandwidth for site deployment should be configured based on the actual site conditions and operational requirements.

## 3. MQTT Connection Specifications

### 3.1 Connection Parameters

|   Parameter Name    |                   Requirement Description                    |                           Remarks                            |

### 3.2 Connection Process

1. The client initiates an MQTT CONNECT request with the connection parameters specified in Section 3.1;
2. The Platform's MQTT server verifies the validity of the parameters (Client ID, Username, Password, etc.);
3. If the verification is passed, the server returns a CONNACK response; if the verification fails, the corresponding error code is returned (refer to Section 7.1 "Connection Error Codes").

## 4. Topic Specifications

### 4.1 Topic Naming Rules

1. Topic levels are separated by slashes (/), e.g., a/b/c;
2. Wildcard subscription is not supported;
3. Topic names do not support spaces, null characters and the following special characters: \0, #, +;
4. The topic length shall not exceed 256 characters.

### 4.2 Topic Definition

This specification defines the following topics, and the access party shall publish data strictly in accordance with the corresponding topics:

|                Topic Name                |           Publisher            | Subscriber |                           Purpose                            | QoS Level  |                           Remarks                            |
| :--------------------------------------: | :----------------------------: | :--------: | :----------------------------------------------------------: | :--------: | :----------------------------------------------------------: |
|  isolarcloud/insight/pub/rundata/5min/{app_key}/enum_0_0_0   | Access party's devices/systems |  Platform  | The access party reports telemetry data of devices/systems to the Platform | QoS 1 or 0 | Telemetry data shall be reported on the hour every 5 minutes |
|  isolarcloud/insight/pub/faultdata/{app_key}/enum_0_0_0    | Access party's devices/systems |  Platform  | The access party reports remote signaling (alarm) data of devices/systems to the Platform | QoS 1 or 0 | All data shall be uploaded for the first link establishment, and subsequent changed data shall be uploaded |
|  isolarcloud/insight/pub/rundata/history/{app_key}/enum_0_0_0 | Access party's devices/systems |  Platform  | The access party supplements and reports historical telemetry data of devices/systems to the Platform | QoS 1 or 0 | Historical telemetry data shall be supplemented and reported on the hour every 5 minutes |

## 5. Message Format Specifications

### 5.1 General Message Requirements

1. Message encoding: UTF-8 encoding shall be adopted;
2. Message format: JSON format shall be uniformly used;
3. Message size: The size of a single message body shall not exceed 64KB.

### 5.2 Data Reporting Message Format

#### 1. Publish Topic: isolarcloud/insight/pub/rundata/5min/{app_key}/enum_0_0_0

**Message Body Structure**:

```

    "sendTime": "20250722105959"//Data sending time in yyyyMMddHHmmss format

    {
      "psId": "3",//Power station code, allocated by the administrator
      "recvTime": "20250722110000002",//Data receiving time in yyyyMMddHHmmss format
```

## 6. Security Specifications

### 6.1 Connection Security

1. SSL/TLS encrypted connection is recommended (corresponding to the SSL/TLS address and port in Section 3.1) to ensure the confidentiality and integrity of data during transmission;
2. Transmitting sensitive data (such as username, password, device key, etc.) through unencrypted channels is prohibited;
3. The access party shall properly keep the username, password, Client ID and other relevant information to avoid leakage; in case of leakage, the access party shall immediately report to the Platform operator and apply for reset.

### 6.2 Data Security

1. The data reported by the access party shall be true and legal; reporting false data, malicious data or data in violation of laws and regulations is prohibited;
2. The Platform will verify the received data; if abnormal data is found, the Platform will reject the data and record error logs; in serious cases, the access permission will be terminated;
3. The access party shall be responsible for the data generated by its own devices and systems to ensure the security and compliance of the data.

## 7. Exception Handling and Error Codes

### 7.1 Connection Error Codes

| Error Code (CONNACK Return Code) |                 Error Description                 |                     Handling Suggestion                      |
| :------------------------------: | :-----------------------------------------------: | :----------------------------------------------------------: |
|                1                 | Connection refused (unsupported protocol version) | Check the client's MQTT protocol version to ensure MQTT 3.1.1 is supported |
|                2                 |      Connection refused (invalid Client ID)       | Check whether the Client ID format complies with the requirements in Section 3.1 and whether there is a duplicate |
|                3                 |      Connection refused (server unavailable)      | Retry later or contact the Platform operator to confirm the server status |
|                4                 |  Connection refused (wrong username or password)  | Check the Username and Password assigned by the Platform; apply for password reset if forgotten |
|                5                 |         Connection refused (unauthorized)         | Check the validity of the access qualification or contact the Platform operator to confirm the permission |

### 7.3 Other Exception Handling

1. **Incorrect message format**: After receiving a message, if the Platform detects an illegal JSON format, missing mandatory fields and other problems, it will discard the message and record an error log; the access party shall ensure that the message format complies with the requirements in Section 5;
2. **Message size exceeding the limit**: If the size of a single message body exceeds the specified upper limit, the Platform will reject the message; the access party shall split the message or compress the data and resend it.

## 8. Test and Acceptance

### 8.1 Test Environment

The Platform normally provides a dedicated test environment, in which the integrating party should complete the required verification before formal production access.

The current test environment is hosted outside Europe. A European test environment is currently under deployment and will be used for European integrations once available.

During this interim period, the integrating party may, subject to prior approval by the Platform operator, transmit a limited amount of data directly to the production environment for connection and data-flow verification.

Such production-environment testing shall be conducted under controlled conditions and shall comply with the following requirements:

1. The test scope, test period, data volume, and participating devices or sites shall be agreed upon in advance with the Platform operator.
2. Only the minimum amount of data necessary for verification may be transmitted.
3. Test data shall be clearly identifiable and, where technically possible, separated from normal production data.
4. The integrating party shall not perform high-frequency, large-volume, destructive, or stress testing in the production environment.
5. The Platform operator shall monitor the test process and may suspend the test if any operational, security, or data-quality risk is identified.
6. Any test records that are no longer required shall be deleted or corrected after the test is completed.

MQTT address and port of the test environment:

[testinsightiot.isolarcloud.com:19999](https://testinsightiot.isolarcloud.com:19999)

[testinsightiot.isolarcloud.com:16668](https://testinsightiot.isolarcloud.com:16668)

To obtain a test account, the integrating party shall submit an application to the Platform operator. The Platform operator will provide the test Client ID, username, password, and other required credentials.


### 8.2 Test Content

1. **Connection test**: Verify whether the client can successfully connect to the test environment server and whether the reconnection mechanism works correctly;
2. **Data reporting test**: Report simulated data to the test environment to verify whether the Platform can receive and parse the data correctly;
3. **Abnormal scenario test**: Simulate scenarios such as disconnection, incorrect message format and permission error to verify whether the exception handling logic of the client and the Platform complies with the specification.

### 8.3 Acceptance Criteria

1. **Connection success rate**: 100% success rate for 10 consecutive connection tests;
2. **Data reporting success rate**: Over 99% success rate for 100 consecutive data reports;
3. **Exception handling**: Under all abnormal scenarios, the client has no crash, and the Platform has no data loss or abnormal log accumulation.
